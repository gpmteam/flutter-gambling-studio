    # UI initialization observation

    Observed in the Phase 4B widget test on 2026-09-30: the direct menu Continue action pushed the gameplay route, whose `didChangeDependencies` immediately called `GameServices.startSession`. That service synchronously publishes run-start statistics. The still-mounted menu's ValueListenableBuilder received the notification while Flutter was building the new route, producing `setState() or markNeedsBuild() called during build`.

    The game screen now schedules its one-time start with `WidgetsBinding.instance.addPostFrameCallback`, checks `mounted`, attaches the session and presentation listeners, and rebuilds after creation. The same real navigation tests then pass the menu-to-game initialization and all eight phone/text geometry cases without framework exceptions. The callback cannot create a session after route disposal.

    Existing UI guidance covers notifier disposal reentrancy, but the searched UI rule/persona/runbook does not document the distinct initialization publication hazard. A bounded improvement could add a route-init example that defers a service call which publishes to other mounted screens, with a real menu ValueListenableBuilder regression scenario.

    This observation is pending framework processing because the delegated Phase 4B contract is limited to the complete UI, targeted verification and handoff. No framework worktree or proposal publication was performed in this phase.
