# Learning proposal: Check every route fills the phone viewport

Status: proposed; human review and merge required.

## Observed problem

A decorated Scaffold body shrink-wrapped its menu child, leaving a dark strip despite clean Chrome manifests.

## Proposed improvement

Add a focused UI audit check requiring every route background and root to fill both edges of the phone column at the four viewport sizes.

Base commit: `67468a8fd24e403ab0a67f8960134167f778cc91`

## Source evidence

### joker-menu-width-evidence.txt

SHA-256: `eadf890a4b0375be9d91ed3bfb16b9d1bbfc20c2dfd3f2d7188d5d07a2b142d2`

    Observation (2026-09-29, Joker's Jewels Phase 10 runtime): Chrome phone captures at 360x640 and 390x844 showed the main menu background and controls painted only to about x=253 logical pixels. The rest of the phone width was a flat dark strip. Splash and gameplay filled the full viewport. Both affected manifests had zero console errors.

    Reproduction: The shared StageScaffold used Scaffold.body: Container(decoration: image, child: SafeArea(child: Column(...))). Its menu Column had no full-width child, so the decorated Container chose the child's intrinsic width under the body's loose constraints. A longer splash text happened to mask the same structural issue on splash. Adding width: double.infinity to the root Container was the immediate fix; post-fix captures are the validation target in the game checkout.

    Existing contract already requires full-bleed phone screens and four-size Chrome review. The gap is that the UI audit checklist checks the game field and the host column but does not explicitly check that every route's own root and background fill the phone column. A focused B-category audit check and runtime-proof reminder would expose this class of bug before release.
