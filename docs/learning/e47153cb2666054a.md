# Learning proposal: Check affordability UI after bet and balance changes

Status: proposed; human review and merge required.

## Observed problem

A state-only builder left NEED CREDITS stale after betIndex or balance changed, even though the HUD updated.

## Proposed improvement

Extend the existing UI audit insufficient-funds check to exercise a bet/balance transition and verify the action control refreshes.

Base commit: `67468a8fd24e403ab0a67f8960134167f778cc91`

## Source evidence

### joker-stale-affordability-evidence.txt

SHA-256: `5a84284b314e6f110b07cfd98d57049dc3e75c7fc133877ee8302bb13aba9b6b`

    Observed in Joker's Jewels Session 3 playtest review, 2026-09-29.
    Before correction, `_ControlDeck` used `ValueListenableBuilder<GameState>(valueListenable: controller.state)` and computed `insufficient` from `controller.balance.value < controller.stake`. `changeBet()` changed `betIndex.value` and called `controller.notifyListeners()` but did not change `controller.state`. Consequently the action label/callback could remain `NEED CREDITS` after a bet tier change made the balance sufficient. `claimDailyBonus()` could also change balance without changing the state notifier. The HUD had its own bet/balance listeners, so it could disagree with the control deck.
    A targeted correction replaced the deck's state-only builder with `AnimatedBuilder(animation: controller)` while keeping its state computation. This observation is about derived UI that depends on more than one notifier; it does not assert a failure in RNG, payouts, or game persistence.
    Existing UI audit D10 checks initial insufficient-funds handling but does not check that affordability feedback updates when balance or bet changes. Proposed remedy: extend that audit with a transition check at the affordability boundary and require the action label/callback to derive from the same live values as the HUD.
